# 接口开发、CRUD 脚手架与交付流程

## 1. 先把需求转成接口契约

新增接口前先明确：

- 资源和操作：查询、创建、更新、删除或状态变更。
- HTTP 方法与路径。
- 请求参数位于 path、query 还是 JSON body。
- 响应字段及统一响应结构。
- 游客、普通用户、管理员分别能否访问。
- 是否存在资源归属、草稿/发布、软删除等业务规则。
- 是否影响缓存、目录树、文章草稿或其他前端状态。
- 是否需要事务、幂等、并发控制或 Redis 原子操作。

不要因为是 CRUD 就默认所有字段都可写，或默认所有登录用户都可操作。

## 2. 后端垂直切片

对一个常规 HTTP 资源接口，按需建立以下链路：

1. `dto`：定义请求和响应契约。
2. `model`：只有新增数据库实体/字段/查询投影时才修改。
3. `repository`：实现必要的数据存取；查询条件只表达存储需求。
4. `service`：实现业务校验、权限相关业务规则和多步骤编排。
5. `handler`：绑定输入、调用 service、映射错误和输出 DTO。
6. `router`：注册路径、方法和正确的中间件。
7. `main.go`：只有新依赖需要构造/注入时才调整。

### CRUD 规则

- 查询：service 决定数据范围和业务可见性；repository 执行查询。
- 创建：service 校验父资源/业务条件，生成业务字段或 ID，再调用 repository。
- 更新：service 校验资源是否存在、用户是否有权修改、状态是否允许变更；repository 执行更新并检查 RowsAffected。
- 删除：先明确软删除/硬删除、级联和引用关系；不得擅自选择。
- 批量操作：评估事务边界和部分失败语义。
- 重复提交：需要时使用唯一约束、幂等键或原子操作，不用前端按钮禁用代替后端保护。

不要机械地为每个字段生成独立 setter 或重复 CRUD wrapper。repository 方法应体现明确的数据访问意图。

## 3. 前端垂直切片

按实际需求选择：

1. `types/<module>.ts`：请求、响应和视图类型。
2. `api/<module>.ts`：封装 API 调用。
3. `hooks/use<Module>.ts`：编排请求、缓存、Store 更新和业务操作。
4. `stores/<module>.ts`：只有状态需要跨组件/路由共享或缓存时才建立。
5. `components/`：复用 UI 与交互。
6. `views/`：页面级数据流和布局。
7. `router/index.ts`：新页面或路由参数时修改。

### 前端数据同步

- API 成功返回后，按业务语义更新 Store。
- 创建资源后，若列表/树已缓存，应同步插入正确节点或让缓存失效。
- 更新实体后同步实体缓存。
- 删除资源后清理实体、列表和相关子节点引用。
- 服务端保存成功后才清理本地草稿。
- 不要将服务端实体、视图树节点和本地草稿混成一个类型。
- 对并发请求和旧响应覆盖新状态的风险进行判断。

## 4. 错误和响应设计

- 成功响应遵循现有 `{ code, msg, data }` 格式。
- 前端 `request` 已经解包 `data`，API 返回类型应描述 data 本身，而不是重复包一层 Response。
- 参数错误、未登录、无权限、资源不存在、冲突、频率限制和内部错误应有不同语义。
- 面向客户端的消息应可理解，但不暴露数据库、Redis、堆栈、Token 或密钥。
- 同一异常只在一个合适边界做日志记录和用户提示。

## 5. 测试矩阵

按功能风险选择测试，不必为了数字追求测试数量。

### Service

- 正常路径；
- 业务校验失败；
- 资源不存在；
- 权限或状态不满足；
- 下游 repository 错误；
- 重复调用/幂等/并发边界（如适用）。

### Repository

- 查询条件正确；
- 空结果与 not found 的语义正确；
- 更新不存在记录时的 RowsAffected；
- 事务、唯一索引、原子操作（如适用）。

### Handler / Middleware

- 参数绑定失败；
- 正常响应和响应字段；
- 401 / 403 / 404 / 409 / 429 / 500 映射；
- OptionalAuth 的游客、有效用户、失效用户、数据库故障分支。

### Frontend

- loading / error / empty / success；
- 重复点击和请求竞态；
- Store 更新和缓存失效；
- 页面切换、组件卸载、请求取消；
- 草稿恢复、保存成功和失败。

项目当前没有完善的前端测试基础设施，若要新增测试框架，先评估范围和依赖成本；不要假装已有测试命令。

## 6. Definition of Done

一个接口/功能完成前，至少确认：

- [ ] 请求和响应契约明确，前后端字段一致。
- [ ] 路由和权限策略正确，不能依赖前端授权。
- [ ] 业务规则在 service，不在 handler/repository 重复实现。
- [ ] repository 不包含业务判断，所有数据库/Redis 操作使用 context。
- [ ] 错误链未被吞掉，HTTP 错误语义合理。
- [ ] 前端复用统一 request，缓存与 Store 同步正确。
- [ ] 空数据、失败、重复请求和边界输入已考虑。
- [ ] 已运行与本次改动相关的验证命令。
- [ ] 最终交付说明实际改动和未验证事项。

## 7. 不做的事情

- 不为简单 CRUD 引入自动代码生成器、通用 DAO 框架或全新 ORM。
- 不把每个 CRUD 都包装成一个只有一行转发的多余 Hook/service。
- 不为每个层级创建空 `errors.go`、接口和单例。
- 不顺手重构无关模块。
- 不未经确认修改数据库 schema、初始化 SQL、生产数据或 API 兼容性。
