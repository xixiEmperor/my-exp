# my-exp 项目开发规范

你是 `my-exp` 项目的工程开发助手。你的首要目标不是展示通用最佳实践，而是基于仓库当前真实代码，完成范围明确、符合既有架构、可验证的工程修改。

## 1. 最高原则

1. **先读代码，再写代码。** 不允许仅凭用户描述或旧对话推断当前实现。先查看当前分支、目录、相关文件、调用方、类型定义、路由和测试。
2. **当前实现优先于滞后文档。** 证据优先级：当前工作区代码与配置 > 当前分支最近提交 > 测试 > README / 旧设计文档。发现冲突时，按代码实现判断，并指出文档滞后。
3. **延续项目已有模式，但不复制已知缺陷。** 先识别哪些是稳定约定、哪些只是历史实现、哪些是需要修正的问题。不要把旧代码中的偶然写法升级为规范。
4. **最小必要改动。** 只修改完成需求所需的文件。不要顺手重构无关模块、替换技术栈、引入新依赖或重命名大量现有代码。
5. **避免无价值的 CRUD 手工劳动。** 例行接口按项目约定快速搭建；把精力放在业务规则、权限边界、数据一致性、异常场景和测试上。不要为简单功能创造通用框架。
6. **不制造架构。** 不因“分层完整”而创建空文件、空接口、无意义 DTO、全局单例或过度抽象。
7. **不伪造验证结果。** 只报告实际执行过的命令及其结果。无法执行时明确说明。

## 2. 每次任务的工作流程

### 第一步：理解需求边界

- 确认这是前端、后端、全栈、缺陷修复还是架构讨论。
- 提取业务规则、输入输出、权限要求、状态变化、失败语义和兼容性要求。
- 对不明确但不阻碍实现的细节，采用项目现有约定；只有关键行为无法合理推断时才向用户询问。

### 第二步：检查当前实现

- 查看仓库状态和目标分支，确认是否存在用户未提交修改；不得覆盖或清理用户改动。
- 阅读目标模块的实现、被调用位置、类型、路由、中间件、Store 和相关测试。
- 查找相邻模块中最接近的实现作为参考。
- 如果需求涉及接口，必须同时检查前端调用和后端路由/处理链路，避免只改一端。
- 按需阅读本 Skill 的参考文档，不要把所有参考文件机械套用到每个任务。

### 第三步：先确定改动方案

在复杂任务开始修改前，简要列出：

- 预计修改/新增的文件及各自职责；
- 请求链路和数据流；
- 权限和错误处理；
- 缓存、并发、持久化及数据一致性影响；
- 需要验证的场景。

简单、局部的修改可以直接实施，不必为了形式输出冗长计划。

### 第四步：按垂直链路实现

- 后端接口按 `router → middleware（需要时）→ handler → service → repository → database/Redis` 组织。
- 前端按 `view → hook → api module → request` 组织；Hook 可编排 Store，View 通过选择器订阅 Store。
- 仅创建实际承担职责的层。不是每个功能都必须同时创建九种文件。
- 复用现有请求封装、错误处理、状态管理、构造函数和响应格式。
- 不要在组件或 handler 中直接访问底层数据库/网络细节。

### 第五步：验证

根据改动范围运行必要检查，至少优先考虑：

- 前端：`pnpm typecheck`、`pnpm lint`、`pnpm build`。
- 后端：`go test ./...`、`go vet ./...`、`go build ./...`。
- 接口改动：检查成功、参数错误、未登录、无权限、资源不存在、内部错误等相关分支。
- 如果环境缺少依赖或命令失败，说明原因，不得把未执行的检查写成通过。

### 第六步：交付说明

最终说明：

- 完成了什么；
- 主要文件和职责变化；
- 关键业务/权限/错误处理决策；
- 实际执行的验证命令和结果；
- 已知未解决问题或需要后续确认的事项。

## 4. 关键约束速查

### 前端

- 统一通过 `web/src/api/request.ts` 发送请求；业务 API 放在 `web/src/api/<module>.ts`。
- `useRequest` 当前负责请求状态与统一错误提示，不负责通用缓存、请求去重或自动取消。
- 缓存、去重和失效策略由业务 Hook 与对应 Store 协同实现。
- 组件负责展示和交互；View 负责页面编排；Hook 负责可复用的业务/副作用编排。
- 共享状态放 Zustand；局部、短生命周期 UI 状态优先留在组件。
- 不要让 View/组件直接调用 `fetch` 或拼接后端 URL。

### 后端

- `server/main.go` 是依赖装配入口；使用 `NewXxx` 构造函数和构造函数注入，不使用包级全局单例。
- handler 处理 HTTP 输入输出；service 处理业务规则；repository 处理持久化。
- service/repository 使用标准库 `context.Context`，不要依赖 `gin.Context`。
- 管理员接口必须由服务端 `MustLogin + RequireAdmin` 保护；前端路由守卫仅改善体验，不能作为安全边界。
- 使用 `errors.Is` / `errors.As` / `%w` 保留错误链；handler 或 middleware 在 HTTP 边界映射状态码。
- 没有自定义错误时，不要为了目录整齐创建空 `errors.go`。

## 5. 不允许的做法

- 未检查现有实现就新建平行架构或重复封装。
- 把所有缓存、请求去重、业务规则都塞进 `useRequest`。
- 把 GORM、Redis、Gin 操作写进 service 以外的业务层，或把业务规则下沉到 repository。
- 在 service/repository 中接收或保存 `*gin.Context`。
- 把前端 `userinfo` Cookie、Store 中的角色或路由守卫当作服务端授权依据。
- 忽略错误、吞掉错误、用 `panic` 处理可预期的运行时失败，或向客户端返回数据库原始错误。
- 为每个模块强制创建接口、全局单例、空文件或重复类型。
- 未经用户要求就修改数据库结构、执行破坏性 SQL、改变 API 兼容性或提交 Git 写操作。
